# Health Module - Specification

Last updated: 2025-11-01 (Plan2 - task 10).

## Goals
- Provide a structured health library to register common ailments, symptoms, and recommended care.
- Track medical records per animal with full history, follow-up reminders, and attachments.
- Connect treatments to the existing planning/notification engine so reminders stay consistent with task templates.
- Work seamlessly offline: creation and updates should be queued locally and replayed when connectivity returns.

## Data Model

### Ailments (`ailments`)
| Field | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key generated server-side. |
| `profile_id` | UUID | Owner profile (RLS enforced). |
| `name` | text | Display name (`Coccidiosis`, `Heat stress`). |
| `slug` | text | Optional import/export identifier, unique per profile. |
| `species_id` | bigint | Optional scope when a disease targets a species. |
| `symptoms` | jsonb | Structured list (`[{code, label, severity}]`). |
| `common_causes` | text | Human readable summary. |
| `recommended_treatments` | jsonb | Array of treatment suggestions (`[{name, description, default_duration_days, default_dosage}]`). |
| `preventive_actions` | text | Free form notes. |
| `created_at` / `updated_at` | timestamptz | Audit timestamps. |
| `archived_at` | timestamptz | Soft delete. |

**Indexes**: `(profile_id, name)`, `(profile_id, slug)` unique, `(species_id)` for filtering.

### Health Records (`health_records`)
| Field | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `profile_id` | UUID | Owner. |
| `animal_id` | UUID | Reference to `animals.id`. |
| `ailment_id` | UUID | Optional link to library (null for custom cases). |
| `custom_diagnosis` | text | Required when `ailment_id` is null. |
| `status` | text | Enum: `draft`, `active`, `resolved`, `archived`. |
| `severity` | text | Enum: `low`, `moderate`, `high`, `critical`. |
| `symptoms` | jsonb | Structured snapshot taken at diagnosis. |
| `notes` | text | Practitioner notes. |
| `onset_date` | date | First observed date. |
| `resolved_at` | timestamptz | Filled when status becomes `resolved`. |
| `next_check_at` | timestamptz | Optional reminder date for follow-up. |
| `created_at` / `updated_at` | timestamptz | Audit timestamps. |
| `offline_reference` | text | Deterministic identifier generated by client to reconcile offline inserts. |

**Indexes**: `(profile_id, animal_id, status)`, `(profile_id, onset_date desc)`.

### Health Treatments (`health_treatments`)
| Field | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `record_id` | UUID | FK to `health_records.id` (`ON DELETE CASCADE`). |
| `profile_id` | UUID | Redundant owner column for RLS. |
| `title` | text | e.g. `Sulfa drug`, `Hydration`. |
| `treatment_type` | text | Enum: `medication`, `procedure`, `care`, `diet_adjustment`. |
| `dosage` | text | Free form dosage instructions. |
| `frequency` | text | e.g. `2x per day`. |
| `start_at` | timestamptz | Planned start. |
| `end_at` | timestamptz | Planned end. |
| `completed_at` | timestamptz | Filled when marked done. |
| `notes` | text | Observations, reactions. |
| `task_id` | uuid | Optional link to `events.id` for planning integration. |
| `reminder_minutes` | integer[] | Offsets passed to notification service (minutes relative to `start_at`). |
| `created_at` / `updated_at` | timestamptz | Audit timestamps. |

**Indexes**: `(record_id, created_at)`, `(profile_id, start_at)`, `(task_id)` unique partial filter to avoid duplicates.

### Projection Views (client side)
- `HealthSummary`: derived DTO inside the app grouping the latest record status, active treatments, and next reminder date per animal.
- `HealthTimelineItem`: merges `health_treatments` and related `events` for display in chronological order.

## Workflows

1. **Library consultation**
   - Farmer opens *Health Library* tab to browse ailments.
   - Search bar filters by name, species, symptoms tags.
   - Selecting an ailment displays description, common symptoms, recommended treatments.

2. **Create a health record**
   - Entry point from animal profile or global FAB.
   - Required fields: animal, status (`active` default), onset date, severity.
   - If the user chooses an ailment template, symptoms and treatment suggestions pre-populate but stay editable.
   - Saving offline: record stored in Drift with `syncState = pending` and enqueued using `SyncActionType.createHealthRecord`.
   - When online, creation also inserts default treatments and schedules reminders through `LocalNotificationService`.

3. **Update record & follow-up**
   - Editing allows status change, new symptoms, progress notes.
   - Switching to `resolved` auto-fills `resolved_at` and cancels open reminders + linked planning tasks.
   - `next_check_at` displays banner and configures a reminder (notifications + optional template task).

4. **Treatment management**
   - From record detail, each treatment can be marked `completed` or `skipped`.
   - Adding a treatment optionally creates a planning task (via `EventRepository`) if a start date is provided.
   - Reminder offsets result in scheduled notifications (delegated to Task 09 service).
   - Treatment timeline shows history grouped by day, referencing tasks completion state.

5. **Offline and conflict resolution**
   - When offline, edits are stored locally with optimistic UI updates.
   - Conflicts resolved by last-update wins; server response merges notes and statuses.
   - Deleting a record cascades to treatments; offline delete retracts pending reminders locally.

## Validations
- `animal_id`, `status`, `severity`, `onset_date` are mandatory for records.
- Either `ailment_id` or `custom_diagnosis` must be provided.
- Cannot set `resolved_at` while status is not `resolved`.
- Treatments must have `title`, `treatment_type`, and `start_at <= end_at` (if end provided).
- Reminder offsets limited to +- 4320 minutes (3 days) to match planning constraints.
- Offline reference must be unique per device to prevent duplicate inserts (UUID v4 recommended).
- UI blocks saving when required fields missing; highlight invalid durations with helper text.

## Offline Mode
- Drift tables mirror Supabase tables (`ailments`, `health_records`, `health_treatments`) with `payload` JSON snapshots.
- Sync queue registers actions:
  - `createHealthRecord`, `updateHealthRecord`, `deleteHealthRecord`
  - `createHealthTreatment`, `updateHealthTreatment`, `deleteHealthTreatment`
- On reconnect the queue executor plays pending actions; failures show in diagnostics log.
- Reminders scheduled locally as soon as treatments are stored (even offline) so device notifications remain consistent.
- When Supabase acknowledges a record created offline, the client replaces the temporary `offline_reference` with the official `id` and updates related treatments/tasks.

## Notifications & Planning Integration
- Treatment creation may spawn a planning task (event) stored in `events` with category `health`. The `task_id` column keeps the backlink.
- Reminder offsets call `LocalNotificationService.scheduleTaskReminder` with payload category `health_treatment`.
- Cancelling or completing a treatment calls `cancelTaskReminder` and marks the linked planning task as done via `EventRepository`.

## UI Screen Guidelines
- **Health Library:** searchable list of ailments, filter chips per species, detail sheet summarising symptoms and preventive tips.
- **Health Record Form:** multi-step layout (Animal selection, Diagnosis, Treatments). Required field markers, offline banner when relevant.
- **Treatment Timeline:** grouped by day with status badges (`Pending`, `In progress`, `Done`, `Skipped`). Each item shows assigned task chip to open the planning detail.
- Empty states emphasise guidance (`No health issue recorded`, `Tap + to log a new case`).

## Security & RLS Notes
- All tables enforce `profile_id = auth.uid()` (same pattern as existing templates).
- Treatments rely on cascading delete; RLS prevents cross-profile access even if users guess UUIDs.
- Ailments may be shared in the future (`visibility` field reserved but not delivered in this iteration).
